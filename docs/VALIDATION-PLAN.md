# DiscForge — Validation plan for the hardware-era backlog

*Draft prepared while awaiting the Plextor PX-W5224TA. Covers the four features held back
because they either need a real drive or need a trusted reference dump to prove correct.
Clean-room throughout: every step below identifies, verifies, reconstructs non-game padding,
or reads the drive's own reported capabilities. Nothing here circumvents, decrypts, or
defeats a protection measure.*

---

## 0. Read this first: what the PX-W5224TA can and cannot do

The PX-W5224TA is a **CD-R/RW drive** (52× read / 52× write / 24× rewrite). It reads Red Book
audio and Yellow/Green Book CD-ROM. It is a strong preservation ripper for CDs specifically:
it reports **C2 error pointers**, has well-characterised cache behaviour, and has a known,
published read-sample offset. It is on Redump's accepted-drive list for CD work.

What it is **not**: a DVD reader, and therefore **not** a GameCube/Wii disc reader (those are a
proprietary mini-DVD format no PC CD drive can address). This matters for sequencing:

- **CD-based features** (`extract-sectors`, the adaptive re-read controller, the drive-capabilities
  profile) are exactly what this drive is for. They are gated on the drive arriving.
- **The GameCube junk-data regenerator is *not* gated on this drive.** It is gated on a *trusted
  reference dump file*, which we may already have. It can likely be validated now — see §1.

So the practical order is: validate the junk regenerator against reference files immediately
(no hardware needed), then do the three CD features as a batch once the drive is on the bench.

## 1. GameCube junk-data PRNG regenerator

### What it does
GameCube/Wii discs fill their unused areas with deterministic pseudo-random "junk", generated by
a lagged-Fibonacci generator (LFG) seeded per-region from the disc's game ID, disc number, and
the region's position on the disc. Because it is deterministic, the junk is *reconstructable*:
tools like NKit drop it to shrink an image and regenerate it on rebuild. DiscForge's regenerator
reproduces those exact bytes so a scrubbed image can be restored to a byte-for-byte Redump match,
and so a full image's padding can be verified as authentic (un-tampered) rather than zeroed or
overwritten.

### Why it was held back
The LFG's seeding and initialisation must be **byte-exact**. Reconstructing it from memory and then
testing it against a fixture I also wrote from memory is a false-validation trap: the two would
agree with each other and still be wrong against real discs. It needs an *independent* ground truth.

### Ground truth — two independent sources, either sufficient
1. **A Redump-verified, unscrubbed GameCube image** (`.iso`/`.gcm`, or `.rvz` decompressed to ISO).
   Read the junk regions directly from the real image and require the regenerator to reproduce them
   bit-for-bit. This is the strongest check — it compares against bytes a real console/drive wrote.
2. **NKit recovery round-trip.** Take an NKit-scrubbed image (its recovery block stores the source
   disc's CRC32 — DiscForge already reads this via `nkit-info`). Regenerate the junk, rebuild the
   full image, hash it, and require the CRC32 to equal the stored source CRC32. This proves the
   reconstruction is exact without needing the original unscrubbed file.

### Protocol
1. Implement the LFG (taps and seed derivation per the documented GC/Wii scheme) behind the existing
   `NkitInfo`/GameCube module, with the seed inputs (game ID, disc number, sector/region index) as
   explicit parameters so they can be unit-fixed.
2. **Source-1 check:** for a verified unscrubbed image, enumerate every junk region (the areas outside
   the filesystem/FST/DOL/apploader extents), regenerate each, and `memcmp` against the image. Require
   100% of junk bytes to match. Log the first mismatching offset if any.
3. **Source-2 check:** for an NKit image, `regenerate → rebuild → CRC32`, and assert equality with the
   recovery block's stored source CRC32. Do this for at least 3 titles spanning both single- and
   multi-disc games (disc number participates in the seed, so a 2-disc title is a required case).
4. Add a **negative control:** flip one byte in a junk region and confirm both checks detect it. This
   proves the check has teeth and isn't trivially passing.

### Pass criteria
- Every junk byte reproduced exactly for ≥1 verified unscrubbed image (Source-1), **and**
- NKit rebuild CRC32 matches the stored source CRC32 for ≥3 titles including one multi-disc title
  (Source-2), **and**
- The negative control is caught.

### What I need from you
One of: a Redump-verified unscrubbed GameCube ISO, **or** any NKit-scrubbed GC image (the recovery
block does the rest). If you have either on `C:\dev` already, point me at it and this one can move now.

## 2. `extract-sectors` (CDRWIN-style disc/track/sector extraction)

### What it does
Extract an arbitrary LBA range (or a whole track) from a CD to a file, at a chosen sector form
(2048 cooked, 2352 raw, +96 subchannel), matching the CDRWIN "Extract Disc/Tracks/Sectors" dialog
you flagged earlier.

### Ground truth
An independent **full** image of the same disc, produced by a trusted tool (a Redump-style DIC dump,
or the drive's own full read via DiscForge's existing dump path). Any sub-range extracted by
`extract-sectors` must equal the corresponding byte slice of that full image exactly.

### Protocol
1. Dump the whole disc once, independently, as the reference (`image[LBA·form_size …]`).
2. `extract-sectors` a set of ranges: a single sector, a track, a cross-track span, the last sector
   (boundary), and an out-of-range request (must error cleanly, not read past lead-out).
3. For each, assert `extracted == reference_slice` byte-for-byte at the requested form.
4. Repeat for a **mixed-mode disc** (data track + audio tracks) so both 2048/2352 data sectors and
   raw audio sectors are exercised, and for one **audio-only** disc.
5. Cross-check one extraction against IsoBuster or CDRWIN's own output on the same range for an
   external sanity tie-break.

### Pass criteria
Byte-exact equality with the reference slice for every in-range request across data, audio, and
mixed-mode discs; clean, non-crashing rejection of out-of-range and malformed requests; correct
handling at track and lead-out boundaries.

## 3. Adaptive re-read controller

### What it does
When a sector reads unstably, escalate: re-read with varied strategy (speed changes, C2-guided
retry, positional jitter) and vote the results into the most-probable true sector, with per-sector
provenance — feeding the existing `reconstruct`/`dump-merge` machinery from live reads rather than
from pre-made image files.

### Why it splits into two tiers
The **decision logic** (when to escalate, how to weight votes, when to declare a sector solved or
unrecoverable) is pure and can be validated in the cloud today with a deterministic error model.
The **hardware integration** (issuing the re-reads, consuming the drive's real C2 pointers and
timing) can only be validated on a real, imperfect disc.

### Tier A — logic harness (do now, no hardware)
1. Build a simulated read source that returns, for a given LBA, a scripted sequence of noisy reads
   plus synthetic C2 pointers drawn from a fixed seed (vary the fixture by index, not RNG).
2. Feed known scenarios: (a) clean sector — must solve on first read, no wasted retries; (b) a
   sector where the true value is recoverable by majority vote after N reads — must converge to the
   true value and stop; (c) an unrecoverable sector — must give up after the configured ceiling and
   mark it unrecovered with provenance, **not** emit a false "solved".
3. Assert the controller's output and its retry count against the scripted expectation for each.

### Tier B — hardware confirmation (on the drive)
1. Use a **known disc with a known-good reference rip** (AccurateRip-verified pressed CD). Introduce
   real read stress with a lightly scratched/marginal disc of the same title if available.
2. Run the controller live; require the recovered image to match the AccurateRip-verified reference
   where the disc is physically readable, and to honestly report the regions it could not recover.
3. Confirm C2 pointers from the real drive drive the escalation (log escalation triggers), and that
   the drive's read offset (from §4) is applied so recovered audio aligns with the reference.

### Pass criteria
- Tier A: correct solved/unrecovered verdict and retry-count for all scripted scenarios, including
  the no-false-positive unrecoverable case.
- Tier B: recovered sectors match the AccurateRip-verified reference; unrecoverable regions are
  reported, never fabricated; escalation is demonstrably C2-driven.

## 4. Drive-capabilities DB / Plextor profile

### What it does
Query a drive for its real capabilities and store a profile: C2 support, cache size and cache-defeat
behaviour, lead-in/lead-out overread capability, and the read-sample offset — so the ripper and the
re-read controller can trust the right parameters per drive instead of guessing.

### Ground truth
The **published profile for this exact model** (Redump's drive list and the AccurateRip drive
database both carry the PX-W5224TA), plus **empirical confirmation** from the drive itself. The read
offset in particular must be confirmed empirically rather than asserted — the plan does not hard-code
a number; it verifies whatever the drive reports against the published value (the PX-W5224TA's read
offset is documented in AccurateRip/Redump; commonly cited as +30 samples — treat that as the
expected value to confirm, not an assumption to bake in).

### Protocol
1. Read capabilities over MMC: `INQUIRY` (vendor/model/firmware), `GET CONFIGURATION` (feature
   descriptors incl. C2), `MODE SENSE` (cache/read parameters). Record what the drive reports.
2. **C2:** verify C2-pointer reads actually return per-sample error flags on a known-marginal disc
   (not just that the feature bit is set).
3. **Read offset:** determine it empirically with an AccurateRip-verified pressed CD — rip, submit to
   AccurateRip, and confirm the offset that yields a confidence match. Assert it equals the published
   PX-W5224TA value.
4. **Overread:** probe how far the drive can read into lead-in/lead-out and record the achievable
   range (relevant to complete first/last-track capture).
5. **Cache:** confirm the cache-defeat strategy works (re-read of a just-read sector genuinely hits
   the disc, not the cache) by timing/consistency, so the re-read controller isn't fooled by cache.
6. Store all of the above as the drive's profile entry and confirm the ripper loads and applies it.

### Pass criteria
Reported capabilities are internally consistent and match the published PX-W5224TA profile; the read
offset is empirically confirmed via AccurateRip and equals the published value; C2, overread, and
cache-defeat are demonstrated on real media, not merely read from a feature bit.

## 5. Recommended sequence

1. **Now, no hardware:** §1 junk regenerator (if a reference GC dump or any NKit image is on hand) and
   §3 Tier A logic harness. Both are fully validatable in the cloud today.
2. **Drive arrives — bring-up:** §4 drive-capabilities/profile first. Everything else depends on
   knowing the real read offset, C2 behaviour, and cache-defeat, so this is the foundation.
3. **Then:** §2 `extract-sectors` (simplest hardware feature, byte-exact ground truth), followed by
   §3 Tier B (adaptive re-read on real, stressed media, using the profile from step 2).

## 6. Definition of done (per feature)

A feature is done when: it passes its pass-criteria above with a **negative control** demonstrated;
it has xUnit coverage shipped for Windows CI (logic tiers) plus a recorded manual bench result
(hardware tiers); `COMMANDS.md` and the version numbers are bumped; and it is synced to
`C:\dev\DiscForge`. Clean-room boundary re-checked at review: identify / verify / reconstruct
padding / read reported capabilities only.
